MarTech Intelligence & Campaign Decision Engine

Every event counted once, every number the AI says is real.

A Go backend that ingests marketing engagement events (sends, opens, clicks, conversions, bounces) from email, SMS, WhatsApp, push and web, turns them into a live engagement score per customer, ranks audiences for the next campaign, and has an LLM explain campaign performance without inventing statistics.

What it does

Five jobs, one pipeline

Ingest

Accept events fast, safely

Batches of up to 500 events per call. Each item is validated on its own, duplicates are counted rather than stored, and the API answers 202 only after the data is durable.

Process

Build customer intelligence

Background workers fold each event into the customer's profile: counters, preferred channel, activity trend, and a decaying engagement score.

Analyze

Campaign analytics

Open, click and conversion rates, per-channel breakdowns and anomaly flags, read from a rollup table so no request scans the raw events.

Recommend

Pick the next audience

Top-K customers for an objective, with score and recency floors, channel filters, frequency caps, and a reason for each pick.

Explain

AI narrative over facts

Go computes the numbers and the LLM only describes them. Output that cites a number Go didn't compute is rejected.

Operate

See and repair failures

A health endpoint shows queue depth and dead-letter size. Failed events can be inspected and replayed through the API.

Architecture

Postgres holds the truth. Redis only moves pointers.

Two binaries built from one codebase: a stateless api and a horizontally scalable worker. They never call each other; they coordinate only through Postgres and Redis.

Solid teal = the durable path. Dashed grey = the fast path, which may fail without losing data. Amber = the AI path, isolated so an LLM outage can't hold API resources.

cmd/api

HTTP server

Gin router, middleware (request ID, access log, body cap), rate limiter, handlers for all 11 endpoints. Runs migrations on boot. With RUN_EMBEDDED_WORKER=true it also runs the worker loop as a goroutine, which suits single-service free-tier deploys.

cmd/worker

Consumer + reconciler

Reads the stream as part of a consumer group, processes each event in one transaction, reclaims stuck messages from dead peers, republishes anything the API failed to publish, and dead-letters poison events.

internal/*

Modules

events ingest + worker · customers scoring · audience top-K · campaigns analytics · ai provider chain · queue stream interface · core middleware & pagination · store pool + migrations.

Seams for later

Request lifecycles

What happens, step by step

The order of each step matters: most of the correctness comes from what happens inside a single transaction and what happens after it commits.

1 · Ingest (write path)

POST /events · internal/events/service.go
  1. Size + rate check. 4 MiB body cap. The token bucket charges len(events) tokens, not 1 per request, so a 500-event batch costs 500.
  2. Per-item validation. Required fields, channel/type enums, occurred_at not in the future. A bad item goes into rejected[{index, reason}] and the rest continue. Malformed JSON → 400 for the whole request.
  3. Resolve ids. Two ANY($1) lookups map every external customer_id/campaign_id to an internal BIGINT. Unknown ids are rejected per item.
  4. One transaction. A multi-row INSERT … ON CONFLICT (event_id) DO NOTHING RETURNING id. A returned row is a new event; no row means a duplicate, which is counted. An event_outbox row is inserted for each new event in the same transaction.
  5. Commit, then answer 202. The event is durable before the client hears back.
  6. Best-effort publish. Pipelined XADD stream:events {event_db_id}, then the outbox row is deleted. If this fails, nothing is lost; the reconciler covers it.

2 · Process (worker path)

internal/events/worker.go · customers/applier.go
  1. Read. XREADGROUP up to 100 messages, spread over 8 goroutines. Periodically XAUTOCLAIM messages idle >30 s, which belonged to a crashed peer.
  2. Lock, then check. SELECT … FROM events WHERE id=$1 FOR UPDATE. If the status is already processed/failed, commit, ack and stop. This is what makes redelivery harmless.
  3. Apply. Lock the engagement_profiles row. Update counters, channel counts, GREATEST(last_event_at) and the anchored decayed score. Insert into sends for sent events, upsert the campaign_metrics daily rollup, and bump customers.last_event_at.
  4. Flip status. status='processed' in the same transaction, then COMMIT, then XACK.
  5. On error. Roll back and record attempts++ and last_error in a separate transaction. At 5 attempts: status='failed' + events_dlq row + XADD stream:events:dlq + XACK.
  6. Safety nets (every ~5 s). The reconciler publishes leftover outbox rows (FOR UPDATE SKIP LOCKED, so workers don't contend). The pending sweeper re-enqueues events stuck in pending for over 30 s.

3 · Read paths

customers · campaigns · audience
  1. Profile. customers ⋈ engagement_profiles. The raw score is decayed to now and normalized s/(s+k) only at read time.
  2. Timeline. Index (customer_id, occurred_at DESC) with a keyset cursor on (occurred_at, id). Pages stay stable when late events arrive, unlike OFFSET.
  3. Analytics. Read from campaign_metrics (campaign × channel × type × day). Cost is proportional to rollup rows, never an events scan. Rates and anomaly flags are computed in Go.

4 · AI analysis

POST /campaigns/{id}/analyze · internal/ai
  1. Cache first. Redis key on campaign + objective + endpoint + prompt_version, TTL 60 s. It is checked before the metrics query, so a hit costs about 1 ms.
  2. Facts in Go. AnalyticsService.Metrics builds a CampaignMetrics struct (counts, rates, per-channel, anomalies). No PII and no raw rows.
  3. Semaphore. Max 8 LLM calls in flight per replica; overflow gets an immediate 429.
  4. Breaker → provider chain. groq → gemini → rule-fallback. A provider whose breaker is open (after 3 straight failures, probed again after 30 s) is skipped instantly.
  5. Validate. JSON schema, confidence ∈ [0,1], and number containment. Invalid output gets one corrective retry, then the next provider.
  6. Always 200. The response is {facts, analysis, provider, fallback_used}, so any degradation is visible to the caller.
Reliability guarantees

Four invariants that carry the design

At-least-once delivery combined with an idempotent consumer is easier to get right than exactly-once delivery, and it gives the same result: each event takes effect exactly once.

No lost events after 202 outbox

The event row and its outbox row commit together. "Committed but not yet published" becomes a state you can query and repair, not a silent loss.

Why: commit and publish to two different systems can't be atomic. The naive version, COMMIT; XADD, loses the event if the process crashes between the two.

Duplicates never double-count UNIQUE

events.event_id UNIQUE is the only dedup authority. The Redis SETNX hint is written after commit and never consulted when classifying duplicates.

Why: an evicted or stale Redis key must never be able to accept a duplicate or reject a legitimate retry.

No partial application one tx

The profile update, rollup, sends insert and status='processed' commit together. Each event is either fully applied or not applied at all.

Why: if the profile committed but the status didn't, a redelivery would apply the event twice and nothing would reveal it.

Redelivery is a no-op lock → check

Status is checked after taking the row lock. Two workers racing on the same event serialize; the second sees processed and acks.

Why: check-then-lock leaves a time-of-check/time-of-use (TOCTOU) window in which both workers see pending.

Failure funnel

# every failure has somewhere to go
XADD fails after commit     → reconciler republishes within ~5 s
stream entry evicted        → pending sweeper re-enqueues after 30 s
worker dies mid-message     → tx rolls back; peer XAUTOCLAIMs after 30 s idle
process tx fails            → rollback, attempts++ (max 5)
attempts exhausted          → status='failed' + events_dlq + DLQ stream + XACK
operator fixes root cause   → POST /system/dlq/{id}/replay
Engagement score

A decaying sum that doesn't care about arrival order

Clients report occurred_at, and mobile or offline sources deliver events hours late. The score is built so the final value is the same in any delivery order.

Definition: each event is worth its weight, fading with a 14-day half-life score(now) = Σ wᵢ · e−λ(now − tᵢ)   λ = ln2 / 14 d ≈ 0.0495 / day In order (t ≥ anchor): decay what you have, then add raw′ = raw · e−λ(t − anchor) + w,   anchor = t Late (t < anchor): decay the new event to the anchor, anchor unchanged raw′ = raw + w · e−λ(anchor − t) At read time only display = s / (s + k),  k = 10,  clamp raw ≥ 0

Both branches update the same closed-form sum, so there's no need to re-sort history. The score is normalized only when displayed: s/(s+k) is nonlinear, so decaying a normalized value would give the wrong answer. Updates are O(1) per event, inside the processing transaction.

Data model

Eight tables, and every index has a named query

Internal BIGINT ids keep joins cheap; clients only see external_id strings. Enums are TEXT + CHECK, so adding a channel is a constraint swap, not a table-locking enum migration.

Audience ranking

Picking the best 50 out of millions without sorting millions

  1. Indexed prefilter in SQL. Score floor, recency, channel and is_active, streamed in engagement_score DESC order from the covering index as an index-only scan. min_score arrives normalized and is converted back to raw units (raw = 10·s/(1−s)).
  2. Bounded pool. LIMIT min(10·size, 200 000). meta.candidates_truncated says whether the cut was reached.
  3. Objective reweighting. raw + a·log1p(conversions) + b·log1p(positive) + c·log1p(days_dormant). For example, conversion boosts converters and reactivation rewards dormancy. Log scaling keeps heavy users from swamping the ranking.
  4. Min-heap of size K. O(N log K) time and O(K) memory. Rows are streamed from pgx and never all loaded at once.
  5. Frequency cap. One batched GROUP BY customer_id over sends in the campaign window for the K survivors. That is 1 query, not K.
  6. Reasons. Explanations are generated only for the survivors, so the cost is O(K), not O(N).
Benchmark (internal/audience/bench_test.go): heap top-K takes 9.3 ms and 341 KB, versus 238 ms and 112 MB for a full sort, at N = 1,000,000 and K = 1,000. That's about 25× faster.
AI layer

The LLM describes the facts. It never produces them.

Every number shown to the user is computed in Go before the prompt is built, and that one decision shapes the rest of the layer.

Guardrail

Number containment

Every number in the model's prose must match a value in facts, or a direct derivation such as rate × 100, within ±0.05 rounding. The model can't cite a statistic Go didn't compute.

Bulkhead

An outage stays contained

A dedicated HTTP client with a 15 s timeout, a semaphore of 8, a per-provider circuit breaker (3 failures → open, 30 s half-open), and a response cache. An LLM outage degrades one feature; it doesn't take down the site.

Fallback

Deterministic templates

If both providers fail, Go templates render the same schema from the same facts. The fallback makes no network calls, so it can't fail. fallback_used: true tells the caller it was used.

Privacy

No PII in prompts, by construction

The AI layer receives a CampaignMetrics struct, not database rows, so a careless prompt edit can't leak an email address. Keeping raw text out of the prompt also narrows the prompt-injection surface.

Weak points

Where this system is weakest, and the fix for each

Taken from the code, not only the docs. Severity reflects the impact at production scale.

High

Single Postgres primary is both the bottleneck and a single point of failure

Symptom
Every write, dedup check, row lock and most reads hit one node. If it's down, ingest returns errors.
Fix
Now: managed HA with a standby and PgBouncer. Next: read replicas, partitioning. Later: shard by customer_id (Citus) or move processing into stream state.
High

Write amplification: about 7 row writes per event

Symptom
Events insert, outbox insert + delete, status UPDATE, profile upsert, rollup upsert and a customers.last_event_at update. That means heavy WAL, dead tuples and autovacuum load, at roughly 7× the event rate.
Fix
Micro-batch the process transaction; replace the table outbox with CDC; drop the per-event customer touch (it's already on the profile); move toward stream processing at 100M.
High

Hot-row contention on campaign_metrics during a blast

Symptom
All events for one campaign/channel/type/day upsert the same row, so parallel workers serialize on its lock. Processing lag spikes exactly when a campaign launches.
Fix
Aggregate deltas per batch in the worker before writing, use sharded counter rows, or compute rollups in ClickHouse/Flink.
High

No authentication, authorization or tenant isolation

Symptom
Anyone who can reach the API can ingest events, read profiles, trigger paid LLM calls or replay the DLQ.
Fix
API keys or OIDC JWT middleware before the router; scopes (ingest vs read vs admin); a tenant_id on every table plus row-level security; audit log for DLQ replays.
Medium

Rate limiter fails open and is keyed by client IP

Symptom
If Redis is down, /events has no throttle at the moment backpressure matters most. Clients behind a shared NAT or proxy share one bucket, and a spoofed X-Forwarded-For can change the IP Gin reports if trusted proxies aren't configured.
Fix
Key buckets by API key; configure Gin trusted proxies; fall back to an in-process limiter when Redis is unreachable instead of allowing everything.
Medium

Redis Streams isn't a durable log

Symptom
Memory-bound, trimmed at ~1M entries, no long replay. Correctness survives (Postgres is the truth), but a Redis failure turns the ~5 s reconciler and 30 s sweeper into the only path, so freshness drops from under a second to tens of seconds.
Fix
Managed Redis with a replica and AOF now; Kafka via the queue interface at 10M+.
Medium

Events for unknown customers are rejected

Symptom
Ingest resolves customer_id against customers, and there's no customer create/upsert endpoint. A web event for a new visitor is dropped as unknown customer_id.
Fix
Upsert unknown customers at ingest (INSERT … ON CONFLICT DO NOTHING), or park them in a pending table; add an identity-resolution step that merges anonymous IDs with known ones.
Medium

Approximate top-K and fewer than K results

Symptom
The candidate pool is cut by raw score before objective reweighting, so a true top-K customer can be missed. The frequency cap runs after the heap, which can return fewer than size.
Fix
Both are reported honestly (candidates_truncated, filtered_out). Improve by oversampling K (e.g. 1.3×K before the cap), indexing an objective-specific score, or precomputing segments.
Medium

AI controls are per replica, not fleet-wide

Symptom
A semaphore of 8 and breakers exist in each process, so 10 replicas allow 80 concurrent calls and each needs 3 failures of its own to trip. Worst-case latency before fallback can reach tens of seconds (15 s timeout per call, one corrective retry per provider).
Fix
An LLM gateway or Redis-backed shared breaker and semaphore; shorter timeouts (the 8B model usually answers in <2 s); an overall deadline across the whole chain.
Medium

Observability is in-process only

Symptom
Counters reset on restart and can't be aggregated across replicas; there's no tracing from ingest to processing.
Fix
Prometheus exporters under the same names; OTel tracing that carries request_id into the stream message; SLO alerts on oldest_pending_age and DLQ growth.
Medium

No right-to-erasure path

Symptom
events, sends and profiles reference customers without ON DELETE CASCADE, so deleting a customer fails. Payloads also live in the DLQ and any Parquet exports.
Fix
A deletion workflow: cascade or tombstone, scrub JSONB payloads, crypto-shred PII by customer key, and propagate deletes to archives.
Low

A late event can't correct last_event_type

Symptom
Counters and score are order-safe, but "latest event type" reflects arrival order, not time order, for late data.
Fix
Update it only when occurred_at ≥ last_event_at (the same guard as GREATEST), or rebuild profiles from events periodically.
Low

Score floor is slightly over-inclusive

Symptom
The prefilter compares min_score against stored, anchor-time raw scores, which haven't been decayed to now, so dormant customers can pass the floor.
Fix
Apply the decay at query time (engagement_score * exp(-λ·(now-score_updated_at))) as a post-filter, or re-anchor idle profiles in a nightly job.
Low

Embedded-worker mode ties processing to the API

Symptom
On free tiers with scale-to-zero, nothing processes until a request wakes the service; a deploy kills in-flight work (safely, but slowly).
Fix
min-instances=1 for demos; separate worker deployments in production.
Low

Rule-based scoring, uncalibrated AI confidence

Symptom
Event weights and objective boosts are hand-tuned constants; confidence is reported by the model, and the fallback is a template.
Fix
Learn weights from conversion outcomes (logistic regression or GBM on profile features), A/B test recommendations, and calibrate confidence against real results.
Questions & answers

What reviewers and interviewers will ask, with answers

DesignWhy is Postgres the dedup authority instead of a Redis SETNX check?

Redis can evict, flush or fail over, and a missing key would let a duplicate through, while a stale key could reject a legitimate retry. INSERT … ON CONFLICT (event_id) DO NOTHING RETURNING id makes the dedup decision in the same statement as the write: one index probe and no extra round trip. The Redis hint is written after commit and is only an optimization.

DesignWhy Redis Streams and not Kafka?

Streams give consumer groups, per-message acks, a pending-entries list and XAUTOCLAIM, which is everything needed for at-least-once delivery with crash recovery, at a fraction of Kafka's operational cost. The stream carries only a pointer (event_db_id), so losing Redis costs latency, not data. Kafka becomes the right answer when you need retention and replay beyond days, more than about 50k msg/s, or lag that survives eviction. The queue.Producer/Consumer interfaces make that a swap of implementation, not a rewrite.

DesignWhy return 202 and not 200 or 201?

202 means "accepted for asynchronous processing". The event is durable when the response is sent, but it isn't reflected in the profile yet (p99 target under 10 s). The body gives exact counts: accepted, duplicates, rejected[].

DesignWhy accept part of a batch instead of rejecting the whole thing?

Rejecting 499 good events because of one bad one punishes good data for bad data and makes clients retry everything. Per-item validation returns rejected[{index, reason}]. The trade-off is that clients must inspect the response. Malformed JSON still fails the whole request with 400.

DesignWhy separate api and worker binaries?

Ingest and processing scale on different axes (request rate vs. processing cost) and should fail independently. A processing backlog shouldn't slow ingest. The same Run() function powers both the standalone worker and the embedded goroutine for single-service demos.

DesignWhy TEXT + CHECK instead of Postgres enums?

Adding a channel such as rcs becomes ALTER … DROP/ADD CONSTRAINT instead of an enum change that can't easily be reversed and has awkward transaction semantics. The database still rejects invalid values.

ReliabilityWhat if the API crashes right after COMMIT but before XADD?

The outbox row was committed in the same transaction as the event. Within about 5 s, a worker's reconciler selects unpublished rows with FOR UPDATE SKIP LOCKED, publishes them and deletes them. The client already has a 202, and the event is processed a few seconds later than usual.

ReliabilityWhat if Redis is completely wiped?

Stream entries are only pointers. Unpublished ones are republished from the outbox, and published-but-unconsumed ones are caught by the pending sweeper (status='pending' older than 30 s). The AI cache becomes a miss and rate buckets refill. Dedup is unaffected because it lives in Postgres. Nothing is lost; latency goes up temporarily.

ReliabilityWhat if a worker dies mid-message?

Its transaction rolls back and the message stays in the consumer group's pending list, un-acked. After 30 s idle, a peer's XAUTOCLAIM takes it over. If the worker died after commit but before XACK, the new owner locks the row, sees processed and just acks.

ReliabilityIs this exactly-once?

Delivery is at-least-once, on purpose: the API and the reconciler can both publish, and reclaims redeliver. The effect is exactly-once because processing is idempotent: lock the event row, check its status, then apply and flip status in one transaction. That's simpler and more robust than distributed exactly-once delivery.

ReliabilityWhy lock-then-check instead of check-then-lock?

With check-then-lock, two workers can both read pending, then both lock in turn and both apply the event. That's a TOCTOU race. Taking FOR UPDATE first serializes them, so the second sees processed. It costs one row lock per message.

ReliabilityHow do you handle poison messages?

Each failure rolls back the work and increments attempts in a separate transaction. At 5 attempts the event is marked failed, copied to events_dlq with payload and error, published to stream:events:dlq, and acked so it can't block the group. POST /system/dlq/{id}/replay re-enqueues it after a fix.

ReliabilityCan two workers deadlock?

The risk is low because lock order is fixed: event row → profile row → sends insert. Locks are held only for the transaction (milliseconds), and statement_timeout (10 s) bounds any stuck query.

Data & scoringHow does the score stay correct when events arrive out of order?

The score is a decayed sum stored as a raw value plus an anchor time. An in-order event decays the stored value to its own time and adds its weight. A late event is decayed to the anchor and added. Both are updates to the same closed-form sum, so the result is the same for any arrival order, with no re-sorting.

Data & scoringWhy store the raw score and not the normalized 0–1 value?

Normalization s/(s+k) is nonlinear, so decaying a normalized number gives the wrong answer. Decay is exponential on the raw sum; normalization happens only for display.

Data & scoringWhy keyset pagination on the timeline?

OFFSET gets slower with depth and shifts when late events are inserted, so users see duplicates or skip rows. A cursor on (occurred_at, id) backed by (customer_id, occurred_at DESC) is stable and uses the index at any depth.

Data & scoringWhy does analytics read a rollup instead of the events table?

events grows forever; a GROUP BY over it per request gets slower every day. The worker upserts campaign_metrics in the same transaction that processes the event, so analytics costs are proportional to rollup rows (campaign × channel × type × day).

AudienceHow do you find the top 50 customers out of millions quickly?

An indexed SQL prefilter (covering index, index-only scan in score order) is capped at min(10·size, 200k) rows. Those rows stream through a min-heap of size K: O(N log K) time and O(K) memory. Then one batched frequency-cap query runs on the survivors. The benchmark shows 9.3 ms vs 238 ms for a full sort at N = 1M.

AudienceWhy might I get fewer customers than I asked for?

The frequency cap is checked after ranking, because checking it for every candidate would be far more expensive. Capped customers are removed and counted in meta.filtered_out. Respecting the cap takes priority over filling the audience.

AudienceIs the ranking exact?

No. The pool is cut by raw score before the objective reweighting, so someone just below the cut could have ranked in after the boost. meta.candidates_truncated says when that cut applied. Exact ranking at multi-million scale belongs in an analytical store or precomputed segments.

AudienceHow does the objective change the ranking?

Log-scaled boosts: conversion adds 0.30·log1p(conversions); engagement adds 0.25·log1p(positive events); reactivation adds 0.30·log1p(days dormant), which rewards lapsed customers with history. Log scaling stops one very heavy user from dominating the list.

AIHow do you stop the LLM from inventing numbers?

Two layers. First, the model never sees raw data: Go computes every metric and passes a facts JSON. Second, number containment: every numeric literal in the output must match a fact or a direct derivation (±0.05 rounding). Otherwise the output is rejected, retried once with a corrective prompt, then the next provider is tried.

AIWhat happens when Groq is down?

After 3 consecutive failures its breaker opens and later requests skip it instantly. Gemini is tried next; if it also fails, the deterministic rule fallback renders the same schema from the same facts. The endpoint still returns 200 with provider:"rule-fallback" and fallback_used:true.

AIWhy does the AI endpoint sometimes return 429?

The semaphore allows 8 in-flight LLM calls per replica. Rejecting the excess immediately protects goroutines, memory, the DB pool and provider spend. Cache hits never use a slot.

AIIs customer data sent to the LLM?

No. The AI layer receives only a CampaignMetrics struct of aggregate counts and rates. That's structural, so a prompt edit can't add emails or names. It also leaves little room for prompt injection, since no user-supplied text reaches the prompt.

ScaleWhat breaks first as traffic grows?

The single Postgres primary. Each event causes about 7 row writes (with WAL and vacuum load), and blasts create a hot row in campaign_metrics. Workers and API pods scale out easily; the database doesn't. See the 10M tab for fixes.

ScaleHow do you scale processing?

Add worker replicas (docker compose up --scale worker=N, or HPA on queue lag). The consumer group splits messages across workers, SKIP LOCKED keeps reconcilers from contending, and row locks make races safe. No code changes are needed.

ScaleWhat about one "hot" customer with a flood of events?

Their events serialize on the profile row lock. That's intentional, because read-modify-write on counters needs it, and other customers keep processing in parallel. At 100M scale, partitioning the stream by customer_id removes the lock entirely: one consumer owns each key.

ScaleHow does the system survive a 10× traffic spike?

Backpressure at every layer: the edge token bucket (cost = events), a 500-item batch cap, the durable outbox, the stream as a buffer, and workers draining at their own pace. Under sustained overload, freshness degrades linearly while correctness holds. 429s push retries to clients, and retries are safe because clients own the idempotency keys.

ScaleHow do you keep the events table from growing forever?

Monthly range partitions on occurred_at, 90 days hot, older partitions exported to Parquet and dropped. A partition drop is instant, unlike DELETE. Analytics history moves to ClickHouse or BigQuery.

Ops & securityHow would you know events are silently not being processed?

Watch oldest_pending_age (the oldest unpublished outbox row or oldest pending stream entry) and dlq_size growth. Queue depth alone can look flat while one event is stuck. /system/health exposes queue_depth and dlq_size today.

Ops & securityHow do you trace a failed request?

Every request gets an X-Request-ID (echoed back), and the access log and every error path include it. Production would carry it into the stream message and OTel spans, so one ID links ingest → worker → DLQ.

Ops & securityWhat about SQL injection and secrets?

All queries are parameterized through pgx ($1…), with no string-built SQL. CHECK constraints bound enum values in the DB. Secrets come from env vars only (.env is gitignored); production uses a secret manager, and nothing secret is logged.

Ops & securityWhat's missing before this goes to production?

Auth (API keys/JWT) with per-key rate limits, multi-tenancy, HA Postgres + PgBouncer, Prometheus/OTel, a GDPR deletion path, customer upsert at ingest, and a fleet-wide LLM gateway. All of these are listed under weak points above.

Glossary

Terms used in this project

Idempotency key event_id
A client-generated unique ID. Sending the same event twice has the same effect as sending it once.
Idempotent consumer
A processor that can safely receive the same message more than once, here via lock-then-check on events.status.
At-least-once delivery
Every message is delivered one or more times; never zero. Duplicates are expected and handled.
Exactly-once effect
Delivery may repeat, but the observable result is as if each event were applied once.
Transactional outbox
Writing a "to be published" row in the same DB transaction as the business data, so publishing can be retried from a durable record.
Reconciler
A worker loop (~5 s) that publishes outbox rows the API failed to publish, then deletes them.
Pending sweeper
Re-enqueues events stuck in pending for over 30 s, covering stream entries lost after publish.
Redis Streams
An append-only log type in Redis, with consumer groups and per-message acknowledgements.
Consumer group
A set of workers sharing a stream; each message goes to one member. Here: event-workers.
XADD / XREADGROUP / XACK
Append to a stream / read as a group member / confirm a message is done.
PEL pending entries list
Messages delivered to a consumer but not yet acked. Survives consumer crashes.
XAUTOCLAIM
Takes over PEL messages idle longer than a threshold (30 s) from another consumer, usually a dead one.
MAXLEN ~
Approximate stream trimming (~1M entries) to cap Redis memory.
DLQ dead-letter queue
Where events go after 5 failed attempts, with payload and error, for inspection and replay.
Poison message
A message that fails every time. Retry caps stop it from blocking the queue.
SELECT … FOR UPDATE
Row lock held until the transaction ends. Serializes concurrent writers on the same row.
SKIP LOCKED
Skip rows already locked by others. Lets many reconcilers share the outbox without waiting.
TOCTOU
Time-of-check to time-of-use race: state changes between checking it and acting on it.
ON CONFLICT DO NOTHING
Postgres upsert variant: silently skip rows that violate a unique constraint. Used for dedup.
Out-of-order (OOO) events
Events whose arrival order differs from their occurred_at order.
Exponential decay / half-life
A value that halves every fixed period (14 days here), so recent activity counts more.
Anchored decay
Storing a raw score plus the time it's valid at, and decaying lazily on the next write or read.
Engagement score
Weighted, decayed sum of a customer's events, shown as s/(s+10) in [0,1).
Rollup
Pre-aggregated counts (campaign × channel × type × day) maintained on write so reads are cheap.
Frequency cap
Maximum sends per customer per window (default 3 per 168 h) to prevent over-messaging.
Top-K / min-heap
Keep only the best K items seen so far in a heap whose root is the weakest; O(N log K).
Prefilter
Cheap indexed SQL filtering that shrinks N before expensive ranking in Go.
Covering index INCLUDE
An index holding every column a query needs, allowing an index-only scan with no table reads.
Partial index
An index over only the rows matching a predicate, e.g. WHERE status='pending'. Small and fast.
Keyset (cursor) pagination
Paging by "after this (occurred_at, id)" instead of OFFSET. Stable and index-friendly.
Token bucket
A rate limiter: tokens refill at a fixed rate up to a burst size; each request spends tokens.
Fail open
When a guard's dependency fails, allow traffic rather than block it. The rate limiter does this if Redis is down.
Backpressure
Letting slower downstream stages push back on (or buffer) faster upstream stages instead of collapsing.
Bulkhead
Isolating a risky dependency's resources so its failure can't sink the rest of the system.
Circuit breaker
Stops calling a failing dependency (open), then probes it again after a cool-down (half-open).
Semaphore
A counter limiting concurrent operations; here 8 in-flight LLM calls.
Provider chain
Ordered failover across LLM providers ending in a fallback that can't fail.
Number containment
Validation that every number in LLM output appears in the computed facts.
Write amplification
One logical write causing many physical writes (rows, index entries, WAL).
Hot row
A single row updated by many concurrent transactions, which then queue on its lock.
Partitioning
Splitting one table into child tables by range (e.g. month) for cheap retention and smaller indexes.
Read replica
A streaming copy of the primary used for read-only queries.
CDC change data capture
Reading the database's WAL to publish changes (e.g. Debezium), an alternative to an outbox table.
Embedded worker
RUN_EMBEDDED_WORKER=true: the worker runs inside the API process for single-service deploys.
statement_timeout
Postgres-side cap (10 s) on any query, so a slow scan can't hold a pool connection forever.
Roaring bitmap
Compressed set of integers with very fast intersections; used for segment membership at 100M scale.
